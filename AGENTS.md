## Critical context

- Reveal historical UK grocery shrinkflation and recipe changes, then forecast monthly changes in price per gram. Familiar snacks and a polished visual demo are central.
- **MONTHLY grocery-price outcomes; WEEKLY commodity inputs.** The user clarified this repeatedly. Do not substitute a seven-day retail target or require weekly grocery-price movements.
- Link product families across old/new barcodes. Different weights or multipack counts may be the change being detected, not a reason to reject a match. Distinguish replacements from concurrently sold variants.
- Preserve sources, raw fields and dates. OFF database edits are not proven market-event dates. Keep candidate matches, verified changes and price observations separate.
- Use real data for model evaluation. Label scenarios/synthetic fixtures clearly; no invented evidence, timelines, backtests or accuracy claims.
- Python preparation/modelling/backtesting and TypeScript UI are agreed. DuckDB/Parquet, boosted trees, MLForecast, React/Vite/Tailwind/Recharts are proposed tools, not installed dependencies.
- Validate a chronological baseline and compare history-only versus commodity/response-pattern features. Previous shrink/price-rise alternation is a hypothesis to learn, not a hard-coded universal rule.
- A large row count is not a long time history. Same-barcode repeat counts also underestimate cross-barcode family coverage; audit both correctly.
- Monte Carlo is an optional calibrated uncertainty/scenario extension.
